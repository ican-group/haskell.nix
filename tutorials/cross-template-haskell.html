Cross-compiling Template Haskell: how it works

TermMeaningGHC’s name
build machinewhere GHC and cabal runhost
host machinewhere the compiled program will runtarget

GHC names machines from the compiler’s point of view; cabal and this page name them from the package’s.

This page is for people who ship GHC or cabal and want cross-compiled Template Haskell (TH) to work. It covers what to build and install: first for plain GHC, then for GHC with a cross-aware cabal. haskell.nix is the reference implementation; links point at its source.

Rows and stanzas marked stable-haskell GHC apply only to the stable-haskell fork of GHC; packagers of upstream GHC can skip them.

The problem

A splice runs while GHC compiles the module. When cross compiling, the splice and everything it calls are compiled for the host machine, and a cross GHC cannot load host code into its own process.

GHC’s answer is the external interpreter: a separate program, built for the host, that loads the splice’s object code and runs it. GHC talks to it over a pipe (the iserv protocol). What is left is starting a host program on the build machine.

The pieces

 build machine
 ─────────────────────────────────────────────────────────────────────
   cross GHC ──(-pgmi)──▶ wrapper script
                              │ exec
                              ▼
                          iserv-proxy                 [build-machine binary]
                              │ starts it under a runner (qemu / wine / hl)
                              ▼
                          iserv-proxy-interpreter     [host binary, emulated]

   GHC ◀── iserv protocol ──▶ proxy ◀── pipe + .o/.a/.so files ──▶ interpreter
  • iserv-proxy sits between GHC and the interpreter. It starts the interpreter and forwards GHC’s messages. When the interpreter asks for an object, archive or DLL it cannot see, the proxy sends the file over. (It can also reach an interpreter on a real device over TCP; haskell.nix only uses the pipe.)
  • iserv-proxy-interpreter is a host executable linked against GHC’s ghci library. It loads host code with GHC’s runtime linker and runs the splice.
  • The runner makes the host binary executable on the build machine.

Both programs come from stable-haskell/iserv-proxy, branch iserv-syms. That branch also compiles a table of libc symbols into the interpreter (cbits/symbols.<host>.c, for musl, Android and Windows), so the runtime linker can resolve them for the code a splice loads.

Step 1: plain GHC

  1. A cross GHC for the host.

  2. iserv-proxy-interpreter, built for the host with that same GHC. It must speak the compiler’s iserv protocol, so build one per GHC version, host and way. It does not depend on the user’s project.

  3. iserv-proxy, built for the build machine with any native GHC.

  4. A runner for the host:

    HostRunner
    any Linux the build machine can’t run nativelyqemu-<arch> (user mode)
    musl Linux, on a macOS build machinehl from hyper-linux (must be installed)
    Windowswine
    a host the build machine can run (e.g. x86_64 musl on x86_64 Linux)none
    JavaScript, WebAssemblyGHC’s own interpreter under node (below)

    A dynamically linked interpreter needs the host’s dynamic loader and libc under qemu: pass the host sysroot (qemu-aarch64 -L <sysroot>, or set QEMU_LD_PREFIX), or link the interpreter statically. haskell.nix links it statically for Android and musl hosts (stable-haskell GHC: libc dynamic, see Appendix A), and dynamically for glibc hosts, where it gets away without a sysroot because the ELF interpreter is an absolute path that exists on the build machine.

  5. A wrapper script per host triple, which GHC starts as -pgmi. The short version (full scripts in Appendix A):

    #!/bin/sh
exec iserv-proxy "$@" --pipe qemu-aarch64 iserv-proxy-interpreter tmp --stdio

  6. The flags, plus the per-host ones:

    aarch64-unknown-linux-gnu-ghc -fexternal-interpreter -pgmi ./iserv-wrapper Main.hs

GHC picks the program by way: it runs <pgmi>-prof for profiled code, <pgmi>-dyn for -dynamic code and <pgmi>-prof-dyn for both (GHC.Runtime.Interpreter.Init). Ship at least the plain and -prof wrappers (the -prof interpreter must be built against profiled libraries). Ship -dyn only if your users build with -dynamic.

JavaScript and WebAssembly

GHC has its own external interpreter for these and always uses it. Don’t set -pgmi.

  • JavaScript: node on PATH.
  • WebAssembly: node on PATH (haskell.nix uses Node.js 24). GHC runs dyld.mjs with one library directory: the last libraries: entry of the C compiler’s -print-search-dirs. libc.so and libffi.so must both be in it; haskell.nix symlinks them into one directory (link).
  • Both load the ghci package at splice time, so it must be built for the host (Step 2).

Step 2: GHC and cabal

This assumes the cabal from the stable-haskell cross-compilation branch (stable-haskell/merge, the cabal side of haskell/cabal#12356).

Every unit in its plan belongs to a machine ("machine" in plan.json):

Built forWhatCompiled by
hosteverything you asked for, including all a splice importsthe cross GHC (--with-compiler)
buildcustom Setup.hs, build-tool-depends executables (alex, happy, hsc2hs, …) and their librariesthe native GHC (--with-build-compiler)

Splices need no build-machine copy of their dependencies: a lens used in a splice is compiled once, for the host, and loaded into the interpreter.

A complete invocation:

cabal build all \
  --with-compiler=aarch64-unknown-linux-gnu-ghc \
  --with-hc-pkg=aarch64-unknown-linux-gnu-ghc-pkg \
  --with-build-compiler=ghc \
  --with-build-hc-pkg=ghc-pkg \
  --with-build-hsc2hs=hsc2hs

with this in cabal.project:

-- Host units only: `package *` would also reach the build-machine units.
package host:*
  ghc-options: -fexternal-interpreter -pgmi /path/to/iserv-wrapper

(haskell.nix wraps ghc to add these flags instead; you don’t need to.) --with-build-PROG sets any other build-machine program.

Per target:

  • JavaScript and WebAssembly: add extra-packages: ghci and leave out the ghc-options above. JavaScript also needs constraints: ghcjs installed (test).

  • WebAssembly: the runtime linker only loads .so files, so host libraries must be shared:

    package host:*
  shared: True

  • Other hosts: a statically linked interpreter loads .a / GHCi .o files, so cabal’s defaults work.

Keep host-only settings (executable-static:, shared:, the flags above) in package host:*.

Build the interpreter without TH-over-iserv, or it depends on itself: the iserv-proxy build must not get the -fexternal-interpreter -pgmi flags.

Appendix A: per-target reference

Wrapper scripts

Linux (qemu or hl), from linux-cross.nix:

#!/bin/sh
set -eu
# GHC passes the pipe file descriptors in "$@".
# `tmp` is the interpreter's storage directory (relative to its working
# directory): files the proxy sends over land there.
exec iserv-proxy "$@" \
  --pipe qemu-aarch64 /path/to/iserv-proxy-interpreter tmp --stdio ${ISERV_ARGS:-}

Use hl instead of qemu-aarch64 on macOS, and the profiled interpreter in the -prof wrapper.

Windows (wine), from mingw_w64.nix:

#!/bin/sh
set -eu
# wine can fail to start if the environment is very large; trim it if so.

# The interpreter and every DLL a splice might load, in one directory.
REMOTE_ISERV=$(mktemp -d)
ln -s /path/to/interpreter/bin/* "$REMOTE_ISERV"
for p in $DLL_DIRS; do            # the host libraries' install directories
  find "$p" -iname '*.dll'   -exec ln -sf {} "$REMOTE_ISERV" \;
  find "$p" -iname '*.dll.a' -exec ln -sf {} "$REMOTE_ISERV" \;
done
# Some DLLs are named libX.dll but loaded as X.dll.
( cd "$REMOTE_ISERV" && for l in lib*.dll; do ln -s "$l" "${l#lib}"; done )

# --no-load-call: wine sees the same files, so the proxy need not copy DLLs.
WINEDLLOVERRIDES="winemac.drv=d" \
WINEDEBUG=warn-all,fixme-all,-menubuilder,-mscoree,-ole,-secur32,-winediag \
WINEPREFIX=$(mktemp -d) \
  exec iserv-proxy "$@" --pipe wine "$REMOTE_ISERV/iserv-proxy-interpreter.exe" \
    tmp --stdio --no-load-call ${ISERV_ARGS:-}

Building the interpreter

One package, built twice from a checkout of iserv-proxy: for the host (the interpreter) and for the build machine (the proxy). cabal reads <project file>.local, so give the host build its own project file:

# Host interpreter: cross GHC, reads cabal.project.host.local (stanzas below).
cp cabal.project cabal.project.host
cabal build exe:iserv-proxy-interpreter \
  --project-file=cabal.project.host \
  --with-compiler=aarch64-unknown-linux-gnu-ghc \
  --with-hc-pkg=aarch64-unknown-linux-gnu-ghc-pkg \
  --with-build-compiler=ghc --with-build-hc-pkg=ghc-pkg

# Build-machine proxy: native GHC, plain cabal.project, none of the stanzas.
cabal build exe:iserv-proxy --with-compiler=ghc

The host stanzas, from overlays/haskell.nix; use the ones for your host. Build the -prof interpreter separately (its own project file, with the last stanza added):

-- GHC >= 9.14: let a splice load even when it references a symbol nothing
-- provides, instead of aborting the whole load.
package iserv-proxy
  ghc-options: -rtsopts=all -with-rtsopts=--optimistic-linking

-- aarch64, GHC < 9.8: the threaded RTS breaks TH with C libraries (th-dlls).
package iserv-proxy
  flags: -threaded

-- Windows: avoid "32 bit pseudo relocation ... out of range" under wine.
if os(mingw32)
  package iserv-proxy
    ghc-options: -debug -optl-Wl,--disable-dynamicbase,--disable-high-entropy-va,--image-base=0x400000

-- Android: qemu can't run Android's dynamic loader, so link statically.
-- Add -optl-no-pie on arm32.
package iserv-proxy
  ghc-options: -debug -optl-static -optl-ldl

-- musl, stable-haskell GHC: a fully static interpreter has no dlsym, so
-- no libc symbol resolves ("Failed to lookup symbol: strlen").  On that GHC
-- executable-static means -fully-static and its runtime linker skips libc.a,
-- so link libc dynamically; Haskell libraries stay static.  Leave out the
-- ghc-options line on fully static hosts (no libgcc_s).
package iserv-proxy
  executable-static: False
  ghc-options: -optl-Wl,--no-as-needed -optl-lstdc++ -optl-lgcc_s

-- The -prof interpreter.
package iserv-proxy
  profiling: True

Android and C libraries. The static interpreter cannot dlopen, and the runtime linker tries a shared object before an archive. Ship only static archives (.a) of the C libraries splices use (link).

Appendix B: how haskell.nix wires this up

For readers who want to dig into the reference implementation.

Hadrian-built cross GHCs get no ghc-iserv (link): every splice except JavaScript and WebAssembly goes through iserv-proxy and a runner, as in Step 1.

The stable-haskell GHC with -target is one native compiler wrapped as a cross compiler with -B<libdir> -target=<triple>; each project builds the host’s boot libraries from GHC’s source (link, link). When the build machine can run host code (x86_64 musl on x86_64 Linux) and the host libraries are static, splices run in-process, with no interpreter. A package that asks for -fexternal-interpreter gets GHC’s own ghc-iserv, built for the host in the same project (link). A glibc GHC can’t dlopen musl .so files, so with shared musl libraries a splice needs the external interpreter. This setup isn’t reproducible outside haskell.nix yet.
