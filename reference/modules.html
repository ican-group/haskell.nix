Haskell.nix

Haskell.nix modules options for packages and components. These are the options the modules argument of a project sets. For the arguments of the project functions themselves (cabalProject', stackProject', shell and flake) see Project options.

!!! note “Generated” This documentation is generated from Nix sources in the modules subdirectory using scripts/options-doc.nix

Configuration Options

The components of a package (packages.<name>.components.sublibs.<name>, .exes.<name>, .foreignlibs.<name>, .tests.<name>, .benchmarks.<name> and .setup) and packages.<name>.allComponent all take the options of packages.<name>.components.library, which are only listed there.

additional-prebuilt-depends

Per-component additional pre-built Haskell packages to make available as dependencies (adds their .conf files to this component’s package DB). Merged with the project-wide prebuilt-depends from cabal-project.nix. Uses a different name from prebuilt-depends to avoid conflicting with the top-level option of the same name in component-driver.nix.

Type: list of package

Default: [ ]

bootPkgs

Packages that, like nonReinstallablePkgs, come from the compiler (rts, ghc-boot-th, ghc-bignum, …); hsPkgs.<name> is null for them.

Type: list of string

Default: [ ]

buildJobs

Number of jobs to pass to Setup build as -jN for this component. null (the default) keeps the standard behaviour of -j capped at min(NIX_BUILD_CORES, 4). Set to 1 to build sequentially (useful for memory-hungry packages that OOM under parallel builds), or to any other positive integer to pin the parallelism.

The v2 (builderVersion = 2) builder passes it to the component’s slice, whose Setup build gets the same -jN. Each library and sublibrary is its own slice (except for build-type: Custom packages, which build as one slice), so to cover a whole package set packages.<name>.buildJobs, which applies to every component on both builders.

Two v1 exceptions:

  • contentAddressed components always build with -j1, because a deterministic output is the point of __contentAddressed. A larger buildJobs is ignored there.
  • ghcjs components pass no -j at all by default. An explicitly set buildJobs is honoured, but leaving it null does not introduce the capped default.

Type: null or (positive integer, meaning >0)

Default: null

buildable

Whether the component can be built: the .cabal file’s buildable: field under the plan’s flags, set by the generated package expression. Components that are not buildable (or not in the plan) are left out of components, checks and shells. Use package.buildable = false to drop a whole package.

Type: boolean

Default: true

configureOptions

Arguments that correspond to cabal.project’s configure-options: stanza. Populated automatically from --configure-option=X entries in plan.json’s configure-args (see modules/install-plan/configure-args.nix) and can also be set directly via modules.

Unlike configureFlags (which flows through Setup.hs configure in the v1 builder), configureOptions round-trips through cabal.project for v2-style builds: v2 emits a per-package configure-options: block so cabal records the value in the UnitId hash and downstream consumers compute matching UnitIds. For build-type: Simple packages cabal wraps each entry as --configure-option=X and Setup.hs silently drops it; for build-type: Configure packages cabal forwards it to the ./configure script. v1 ignores this option entirely.

Type: list of string

Default: [ ]

generateOptparseApplicativeCompletions

Install bash, zsh and fish completion scripts for an executable built with optparse-applicative, by running it with --bash-completion-script, --zsh-completion-script and --fish-completion-script, and installing them with nixpkgs’ installShellCompletion (in share/bash-completion/completions, share/zsh/site-functions and share/fish/vendor_completions.d).

Only applies to exes components. Set it on one exe (packages.foo.components.exes.foo.generateOptparseApplicativeCompletions = true;) or on a package to cover all of its exes (each must then use optparse-applicative, or the build fails). Do not set it for the whole project: that covers every exe in the plan, build tools such as alex and happy included.

The scripts are generated in a separate derivation that links to the exe, so turning this on does not rebuild it. The exe has to run on the build machine: a cross compiled exe is run through the component’s testWrapper (an emulator), and when there is none (or the host is Windows, JavaScript or WebAssembly) the exe is left as it is, without completions (as nixpkgs’ generateOptparseApplicativeCompletions does when cross compiling). haskellLib.addOptparseApplicativeCompletions adds them to any exe component derivation directly.

Type: boolean

Default: false

See Note [prebuilt dependencies] for more details

Type: list of package

Default: [ ]

profilingDetail

The --profiling-detail used when profiling is on (for example "default", "all-functions", "toplevel-functions"). Not used by builderVersion = 2.

Type: null or string

Default: "default"

programOptions

Per-program option arguments that correspond to cabal.project’s <prog>-options: stanzas (e.g. c2hs-options:, hsc2hs-options:). Populated automatically from --<prog>-option=X entries in plan.json’s configure-args (see modules/install-plan/configure-args.nix) and can also be set directly via modules.

v2 emits each (prog, options) pair as a package <pkg> block with a <prog>-options: line so cabal-install threads the values through to the program’s ProgramDb at build time — configure-options: would be silently dropped here because it only applies to build-type: Configure packages. v1 reads configureFlags directly (which retains the --<prog>-option=... form) and ignores this option.

Type: attribute set of list of string

Default: { }

projectPackages

Like localPackages, but only for packages with package.isProject set: the project’s own packages, not those from source-repository-package stanzas. For example, to build them with -Werror (only in the Nix build, not when using cabal in a shell): projectPackages = { ghcOptions = [ "-Werror" ]; };.

Type: package options (as for packages.<name>), or a module function returning them

Default: [ ]

reinstallableLibGhc

Is lib:ghc reinstallable?

Type: boolean

Default: true

setup-depends

pkgs to globally provide to Setup.hs builds

Type: list of unspecified value

Default: [ ]

setupBuildFlags

Extra arguments for Setup build. Not used by builderVersion = 2.

Type: list of string

Default: [ ]

setupHaddockFlags

Extra arguments for Setup haddock, when building the component’s documentation. Not used by builderVersion = 2.

Type: list of string

Default: [ ]

setupInstallFlags

Extra arguments for Setup install. Not used by builderVersion = 2.

Type: list of string

Default: [ ]

shellHook

Hook to run when entering a shell

Type: unspecified value

Default: ""

testFlags

Extra command-line arguments passed to the test executable when its check (hsPkgs.<pkg>.checks.<name>) runs it. See docs/tutorials/testing.md.

Type: list of string

Default: [ ]

testWrapper

A command (as a list of words) that a test’s check runs the test executable with, taking the test command and its arguments as its own arguments. Used to run cross-compiled tests under an emulator.

Type: list of string

Default: [ ]

Example:

[
  "echo"
]

usesTemplateHaskell

Declare that building this component runs Template Haskell splices. When cross compiling (builder v2) for a dynamically linked musl host, such a component is built with -fexternal-interpreter: the in-process interpreter cannot load musl shared objects into the glibc compiler. Nothing can tell ahead of time whether a component will evaluate a splice, so this has to be said by whoever knows – e.g. in a project’s modules: packages.th-orphans.components.library.usesTemplateHaskell = true;

Type: boolean

Default: false

writeHieFiles

Write component .hie files in the store in a hie output

Type: boolean

Default: false
