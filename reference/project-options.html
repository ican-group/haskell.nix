Haskell.nix

Project options

These are the arguments of cabalProject', stackProject' and project' (and their unprimed versions). The project functions take a module, so an argument can also be a list of modules or a function of { config, pkgs, lib, ... }, and appendModule adds more modules to a project:

pkgs.haskell-nix.cabalProject' [
  { src = ./.; compiler-nix-name = "ghc912"; }
  ({ config, ... }: { shell.tools.cabal = "latest"; })
]

The modules argument is different: it sets the options of the package set, which are on the Module options page.

!!! note “Generated” This page is generated from the Nix sources in modules by scripts/project-options-doc.nix.

Options of every project

builderVersion

Selects which component builder is used for per-component derivations.

  • 1 (default) — the Setup.hs-based builder (comp-builder.nix).
  • 2 — the cabal v2-build-based slicing builder (comp-v2-builder.nix). This is project-wide. Set it on the project module to switch builders; there is no per-component opt-in.

Type: signed integer

Default: 1

crossPlatforms

The cross-compilation platforms of the project, selected from pkgs.pkgsCross-like platforms (see lib.systems.examples in nixpkgs). The default for shell.crossPlatforms and flake.crossPlatforms.

Type: unspecified value

Default: p: [ ]

Example: p: [ p.ghcjs p.mingwW64 ]

evalPackages

Packages used to run cabal and nix-tools, derived from evalSystem via the memoised haskell-nix.evalPackages attrset. Defaults to pkgs.pkgsBuildBuild when evalSystem matches the pkgsBuildBuild system (the common case), otherwise a shared nixpkgs imported for evalSystem from the same path and overlays. Select the eval platform with evalSystem rather than setting this directly; setting it is deprecated and gives a warning.

Type: attribute set

Default: pkgs.haskell-nix.evalPackages.${config.evalSystem}

evalSrc

Allows a different version of the src to be used at eval time. This is useful when building the source may require a build machine. To avoid an eval time dependency on a build machine set evalSrc to either:

  • A version of the source built using evalPackages
  • A version of the source that does not require building

Type: absolute path or package

Default: config.src

evalSystem

Specifies the system on which cabal and nix-tools should run. If not specified the pkgsBuildBuild system will be used. If there are no builders for the pkgsBuildBuild system specifying a system for which there are builders will allow the evaluation of the haskell project to work.

Type: string

Default: the system of pkgs.pkgsBuildBuild (or of evalPackages, when that is set)

hpack

The hpack that turns package.yaml files into .cabal files, for the packages of a cabal project (supportHpack = true) that have no .cabal file. When it is set, it runs on the project source (the whole source, as the source filter leaves it) in a step of its own, and the .cabal files it writes are what plan-to-nix reads and what the packages are built with (the builders do not run hpack again), so the plan and the build always agree. Editing a source file re-runs only that hpack step; the project is only planned again when a generated .cabal file changes.

A version string (pin it, e.g. "0.38.1"), or other haskell-nix.tool arguments (an attribute set, a module list or a function), builds that hpack with haskell-nix.tool and the project’s compiler, on evalSystem (so each compiler builds its own hpack before the project can be planned). A derivation with bin/hpack is used as it is; it must run on evalSystem. null (the default) uses the hpack that ships with nix-tools, which the builders also run.

Stack projects ignore it (with a warning): stack-to-nix plans with its own built-in hpack.

Type: null or package or string or (attribute set) or list of unspecified value or function that evaluates to a(n) unspecified value

Default: null

Example: "0.38.1"

ignorePackageYaml

If set, prevents nix-tools from attempting to load package.yaml even if it is present.

Type: boolean

Default: false

injectStableHaskellBootPackages

Inject the stable-haskell GHC’s boot package sources (source-repository-package on the configured GHC tree, exact version pins for the hackage-resolved boot deps, and the stage3-style project configuration) into the project’s cabal.project, so cabal plans and builds rts, base, … from source alongside the project’s own packages.

null (the default) auto-detects: the injection is applied exactly when the selected compiler is a stable-haskell -target cross wrapper (passthru.emptyGlobalPackageDb), whose global package db ships no boot libraries. See modules/cabal-project.nix for the wiring.

Type: null or boolean

Default: null

name

Optional name for better error messages

Type: null or string

Default: "haskell-project"

silenceOrgMoveWarning

Hide the warning shown when the project’s flake.lock, niv or npins pins still reference haskell.nix (or hackage.nix / stackage.nix) under its old GitHub owner.

Type: boolean

Default: false

src

The project’s source: the directory with the cabal.project (or stack.yaml) file and the packages. Often filtered, for instance with haskellLib.cleanGit or haskellLib.cleanSourceWith.

Type: absolute path or package

useLocalGhcLib

Expose the GHC compiler tree (configured-src + generated, the compiler/ subdir thereof) to the planner as a regular reinstallable package source. Use this when the project depends on / constrains the ghc package — e.g. ghc-lib-reinstallable.

The project-level wiring differs by builder:

  • Cabal projects (see modules/cabal-project.nix) inject a source-repository-package block into cabalProjectLocal so cabal hashes the wrapped repo’s content into pkg-src-sha256. Both plan-to-nix and the v2 slice see the same repo, so UnitIds align.
  • Stack projects (see modules/stack-project.nix) re-add the post-plan packages.ghc.src override that modules/configuration-nix.nix used to apply unconditionally — stack only supports the v1 builder for now, so the post-plan override is harmless (v1 doesn’t enforce UnitId alignment).

Type: boolean

Default: false

v2LocalPackageSliceNames

Package names whose LIBRARY slices are built in cabal packages: mode, as v2LocalPackageSlices does for every local unit, but without that option’s other project-wide effects (the solver’s view of the compiler’s global db). Set by the stable-haskell boot injection for ghc, whose unit id GHC itself hard-codes. Only meaningful with builderVersion = 2.

Type: list of string

Default: [ ]

v2LocalPackageSlices

Build v2 slices for style: "local" plan units in cabal packages: mode instead of extra-packages: mode, so each slice’s cabal elaborates — and REGISTERS — the same deterministic local unit id the project plan records (base-4.22.0.0, rts-1.0.3-threaded-nodebug, …), and the slice/plan unit-id equality check is enforced for them.

Set by the stable-haskell stage2 boot-library project: its slices’ registered ids become the compiler’s global package db, which consumer projects’ plan-time dummy ghc-pkg dump must be able to predict (an extra-packages: slice registers an unpredictable hashed id instead). Only meaningful with builderVersion = 2.

Type: boolean

Default: false

prepopulateHackageIndex

Whether to prepopulate the full Hackage index (~1.2 GB, truncated to the project’s index-state) into the CABAL_DIR used for plan-to-nix.

cabal parses this index at startup on every invocation — even with active-repositories: :none — so for projects that resolve nothing from Hackage (every dependency pinned as a local package or source-repository-package, e.g. via replace-hackage-tarball-urls), the full index is a large, needless cost (seconds natively, minutes under emulation). Set this false for such projects to prepopulate an empty index instead, which cabal loads instantly. Leave true (the default) for normal projects that resolve dependencies from Hackage.

Type: boolean

Default: true

replace-hackage-tarball-urls

When enabled, rewrite direct Hackage tarball URLs in the cabal.project packages: stanza — of the form https://hackage.haskell.org/package/NAME-VER/NAME-VER.tar.gz — into local nix store paths fetched via hackage.nix (haskell-nix.hackageTarball).

This lets cabal use the exact pinned versions without network access during plan-to-nix, and without the version needing to be present at the project’s index-state (hackage.nix carries the sha256 for the exact version). Off by default; enable for projects (such as the stable Haskell GHC build) that pin dependencies via direct Hackage URLs.

The plan-to-nix rewrite uses evalPackages (the tarballs are only read at eval time), while each found package’s build src is overridden to the content-identical buildPackages tarball, so the built derivation stays independent of the eval platform.

Type: boolean

Default: false

sha256map

An alternative to adding --sha256 comments into the cabal.project file: sha256map = { “https://github.com/jgm/pandoc-citeproc”.“0.17” = “0dxx8cp2xndpw3jwiawch2dkrkp15mil7pyx7dvd810pwc22pm2q”; };

Type: null or (attribute set of (string or attribute set of string))

Default:

{
  "https://github.com/pepeiborra/ekg-json" = {
    "7a0af7a8fd38045fd15fb13445bdcc7085325460" = "sha256-fVwKxGgM0S4Kv/4egVAAiAjV7QB5PBqMVMCfsv7otIQ=";
  };
}

source-repo-override

Changes to the source-repository-packages of the cabal.project: a function, by repository url, from the stanza’s data to its replacement. Useful because cabal does not let a cabal.project.local replace a source-repository-package (for instance to test against the latest version of a dependency).

Type: attribute set of function that evaluates to a(n) (attribute set)

Default: { }

Example:

{ "https://github.com/input-output-hk/plutus-apps" =
    orig: orig // { subdirs = (orig.subdirs or [ "." ]) ++ [ "foo" ]; }; }

supportHpack

Run hpack on the package.yaml of packages that have no .cabal file (see hpack).

Type: boolean

Default: false

usePatchedHsc2hs

Offer cabal’s solver haskell.nix’s patched hsc2hs as hsc2hs-${pkgs.haskell-nix.hsc2hs-patched-version}, from a small package repository added to the project (haskell-nix-hsc2hs). It is stable-haskell’s batch cross-compilation fork of hsc2hs with haskell.nix’s fix to it (see overlays/hsc2hs.nix), which makes cross-compiled .hsc files much faster to process – around 15x for the GHC JavaScript backend and 20x for wasm.

It is only a candidate. It is chosen when a plan needs hsc2hs as a build tool (build-tool-depends or the legacy build-tools) and the version satisfies the constraints on it; otherwise cabal picks another version as usual. Packages that do not ask for hsc2hs keep using the compiler’s.

A project that sets active-repositories has to list haskell-nix-hsc2hs itself for the repository to be used.

Type: boolean

Default: true

withBuildCompiler

Pass a build-platform dummy ghc + ghc-pkg to make-install-plan during plan-to-nix, via --with-build-compiler / --with-build-hc-pkg (the stable-haskell cabal fork’s cross “stage” system, haskell/cabal#11179).

The build dummy’s ghc --info reports the build (native) platform and its ghc-pkg dump --global lists the build boot libraries (especially ghc-internal) as installed. That satisfies a source project’s constraints: build:any.ghc-internal installed and lets cabal resolve build-tool-depends (e.g. hsc2hs) in the build scope, reusing the installed build-stage process/base rather than rebuilding them — breaking cross build-tool cycles (e.g. the Windows Win32 -> hsc2hs -> process -> Win32 cycle) without the full Hackage index. Off by default; projects that don’t set it get no --with-build-compiler (unchanged behaviour).

Type: boolean

Default: false

gitExtraDepsLocal

Treat the packages from git extra-deps in the stack.yaml file as local packages (package.isLocal, but not package.isProject), the same as a cabal.project source-repository-package. Git packages that come from a custom snapshot (a .yaml resolver) are not affected, and nor is a package whose name is also given by a later snapshot entry (the snapshot’s source is the one used).

Use this when a cabal.project next to the stack.yaml builds the git dependencies from their source (for instance with source-repository-package stanzas). Then:

  • shellFor (and selectLocalPackages) include these packages, so the shell provides their dependencies and leaves out the packages themselves and every package that depends on them; cabal builds them from the source the cabal.project points at. Without such a cabal.project, cabal build in the shell has nowhere to find them.
  • The shell also provides the dependencies of their test suites and benchmarks (as for any local package), which may pull in test frameworks the project itself does not use.
  • localPackages module options (-Werror for instance) apply to them too.

Type: boolean

Default: false

inputMap

Specifies the contents of the git urls referenced by the extra-deps in the stack.yaml file. This is the stack equivalent of the cabalProject inputMap argument and is the recommended way to make private git repositories (served over ssh/git) and fully offline builds work.

Keys are the repository url (optionally suffixed with /<rev>) and values are the corresponding local path or flake input. When a key of the form <url>/<rev> is present the value is used directly. When a bare <url> key is used the value’s .rev attribute is checked against the commit in the stack.yaml file.

For example: inputMap = { “https://github.com/jgm/pandoc-citeproc” = inputs.pandoc-citeproc; };

Type: null or (attribute set)

Default: { }

shell.exposePackagesVia

How the v2 shell’s pre-built library deps are made visible to tools the user runs. One of:

  • “cabal-store” (default) — the composed store is linked into the cabal store (cabal path --store-dir) via a shellHook (or the explicit haskell-nix-cabal-store-sync command). cabal v2-build then reuses the units directly. The shell’s ghc is left plain, so runghc/ghci will not see the deps.

flake.coverageProjectModule

Project module for use when generating coverage reports. The coverage jobs turn coverage on for the project packages:

  • builderVersion = 1: they set packages.X.doCoverage. To leave a package out, give it a plain definition here (modules = [{ packages.X.doCoverage = false; }]); a lib.mkDefault false is not enough.
  • builderVersion = 2: doCoverage alone is ignored (coverage has to be in the plan), so they add package X / coverage: True to cabalProjectLocal. To leave a package out, add package X / coverage: False to cabalProjectLocal here (it comes after theirs, so it wins). Setting packages.X.doCoverage = false conflicts with the plan’s true.

Whether a project is v2 is read from the project with this module applied, so a module that sets builderVersion is honoured.

Type: unspecified value

Default: { }
